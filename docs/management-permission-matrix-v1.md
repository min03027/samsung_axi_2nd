# 통합 관리자 플랫폼 권한 매트릭스 v1

> 문서 상태: 구현 전 설계안
>
> 대상: 강사(INSTRUCTOR), 운영관리자(ADMIN), 최고관리자(ADMIN 중 별도 등급)
>
> 범위: 권한·데이터 범위·민감정보 정책 정의
> 제외: Role/DB/SecurityConfig/Controller/Service/메뉴의 실제 변경

이 문서는 현재 코드에서 실제로 동작하는 권한과 앞으로 적용할 목표 권한을 구분한다. 표의 권한은 구현 완료 상태가 아니라 **다음 단계의 구현 기준**이다.

## 1. 현재 실제 Role 구조

### 1.1 현재 Role과 로그인 이동

현재 `Role`은 다음 세 종류뿐이며 사용자 한 명은 하나의 Role을 가진다.

| 현재 Role | 로그인 후 이동 | 주 용도 |
|---|---|---|
| `TRAINEE` | `/trainee` | 수강생 플랫폼 |
| `INSTRUCTOR` | `/instructor` | 강사 플랫폼 |
| `ADMIN` | `/admin` | 운영관리자와 최고관리자를 모두 포함 |

`LoginUser`는 Role 하나를 `ROLE_{ROLE}` 권한으로 변환한다. 운영관리자와 최고관리자를 구분하는 DB 필드나 별도 권한 묶음은 없다.

### 1.2 현재 URL 접근 제어

`SecurityConfig`의 핵심 규칙은 다음과 같다.

| URL 영역 | 현재 허용 Role | 비고 |
|---|---|---|
| `/admin/evaluation/**` | ADMIN, INSTRUCTOR | 문제은행·시험·과제·채점·감독을 공유 |
| `/admin/support/**` | ADMIN, INSTRUCTOR | Q&A·튜터링을 공유 |
| `/admin/notice/**` | ADMIN, INSTRUCTOR | 공지·알림을 공유 |
| `/admin/survey/**` | ADMIN, INSTRUCTOR | 설문 관리와 결과 다운로드를 공유 |
| 그 외 `/admin/**` | ADMIN | 운영관리자와 최고관리자 구분 없음 |
| `/instructor/proctor/**` | ADMIN, INSTRUCTOR | 감독 기능 공유 |
| `/instructor/**` | ADMIN, INSTRUCTOR | ADMIN도 강사 화면 접근 가능 |
| `/trainee/**` GET | TRAINEE, ADMIN | ADMIN은 수강생 조회 화면 접근 가능 |
| `/trainee/**` 쓰기 | TRAINEE | 수강생 본인 기능 |

메서드 권한을 적용하는 `@EnableMethodSecurity`는 현재 활성화되어 있지 않다. 따라서 현재 권한은 크게 다음 세 방식이 혼재한다.

1. `SecurityConfig`의 URL별 Role 검사
2. Controller/Service의 수동 Role 검사
3. Repository 조회 조건 또는 Service의 담당 과정 검사

### 1.3 현재 담당 범위가 실제로 제한되는 기능

| 기능 | 현재 서버 제한 방식 | 평가 |
|---|---|---|
| 강사 과정/수강생 | 강사 배정 과정 ID 및 해당 과정 수강생으로 조회 | 양호 |
| 강사 일정 | 담당 과정 검사 후 조회 | 양호 |
| 강사 출결 | 담당 과정 ID만 조회, 타 과정 요청 시 403 | 양호, 현재 읽기 중심 |
| 강사 수료 현황 | 담당 과정 ID만 조회 | 양호, 판정·확정은 ADMIN 경로 |
| 공지 | 강사는 담당 과정 공지만 생성·수정·삭제 가능 | 양호 |
| 시험 목록·수정 | 담당 과정 범위 검색과 관리 검사 존재 | 대체로 양호 |
| 시험 채점 | 강사 여부와 담당 과정 검사를 Service에서 수행 | 대체로 양호 |
| 시험 감독 | 담당 과정 검사, 응시 무효 처리는 ADMIN만 허용 | 양호 |
| 설문 결과 다운로드 | 강사는 담당 과정 설문인지 검사 | 양호 |
| Q&A·튜터링 | 강사는 본인에게 배정된 건만 목록·상세 접근 | 양호. 과정 범위보다 담당자 중심 |

### 1.4 현재 발견한 권한 공백과 불일치

| 영역 | 현재 문제 | 위험 |
|---|---|---|
| 콘텐츠 관리 | `/instructor/contents/**`가 로그인 사용자나 담당 과정 검사를 사용하지 않고 전체 과정·콘텐츠를 조회/변경할 수 있음 | 강사가 타 과정 콘텐츠를 변경할 수 있음 |
| 문제은행 | ADMIN·INSTRUCTOR가 공용 전체 문제를 조회·등록·수정·비활성·삭제·엑셀 다운로드함 | 소유자·공유·담당 과정 정책 부재 |
| 과제 관리 | 목록은 강사 담당 과정으로 제한되나 생성·상세·수정·마감·삭제와 첨부파일 다운로드의 객체 단위 검사가 일관되지 않음 | URL/ID 변경으로 타 과정 데이터 접근 가능성 |
| 시험 생성 | 수정·상태 변경에는 담당 검사 함수가 있으나 생성 경로가 담당 과정 생성 검사를 호출하지 않음 | 조작된 요청으로 타 과정 시험 생성 가능성 |
| 설문 관리 | 결과 다운로드만 담당 과정 검사. 목록·생성·수정·상태·삭제는 강사 범위 제한이 없음 | 타 과정 및 전체 설문 변경 가능성 |
| 관리자 계정 | `/admin/admins/**`는 모든 ADMIN이 접근 가능 | 운영관리자가 다른 관리자 계정을 관리할 수 있음 |
| 최고관리자 식별 | 설정값 `lms.admin.super-login-id`, 기본값 `admin`과 로그인 ID가 같으면 최고관리자로 판단 | 계정명에 권한이 결합되고 다중 최고관리자·위임·회수·감사에 취약 |
| UI 권한 | 일부 메뉴는 `sec:authorize` 또는 `superAdmin` 모델 값으로 숨김 | 메뉴 숨김만으로 직접 URL/API 접근은 차단되지 않음 |

현재 최고관리자 전용 서버 검사는 계정 로그인 정보 변경(`/admin/accounts/{id}/credentials`)에서 명시적으로 수행된다. 해당 화면 버튼도 `superAdmin` 모델 값으로 숨기지만, 서버 차단은 Controller의 `requireSuperAdmin`이 담당한다. 반면 관리자 계정 목록·생성·수정 전반은 최고관리자 전용이 아니다.

## 2. 목표 Role 구조

### 2.1 사용자에게 보이는 세 역할

| 목표 역할 | 책임 | 기본 데이터 범위 |
|---|---|---|
| 강사 | 배정받은 과정·반·학생의 학습과 생활 지도 | 담당 범위 |
| 운영관리자 | 교육 운영 전반, 과정·학생·강사 배정·평가·상담·취업 운영 | 기관 전체 운영 데이터 |
| 최고관리자 | 운영관리자 권한 + 계정·권한·시스템·민감 교육 인사 데이터 통제 | 기관 전체 및 감사 대상 데이터 |

### 2.2 권장 기술 모델

최종 권장안은 **현재 Role을 로그인 영역(persona)으로 유지하고, 관리자 등급과 세부 Permission, Data Scope를 분리하는 방식**이다.

```text
Role: TRAINEE | INSTRUCTOR | ADMIN
AdminLevel: OPERATOR | SUPER            // ADMIN에게만 적용
Permission: 기능 단위 권한             // 예: STUDENT_DIARY_WRITE, ADMIN_ACCOUNT_MANAGE
DataScope: 데이터 범위                  // 예: ASSIGNED_COURSE, INSTITUTION_ALL
```

검토한 대안은 다음과 같다.

| 대안 | 장점 | 단점 | 판단 |
|---|---|---|---|
| 로그인 ID로 최고관리자 판별 | 현재 변경량이 작음 | 권한 위임·회수·다중 계정·감사에 부적합 | 폐기 권장 |
| `ADMIN + adminLevel`만 적용 | 현재 구조에 가장 적은 변화 | 기능별 예외가 늘면 조건문이 증가 | 1차 이행에 적합 |
| Role을 `OPERATOR_ADMIN`, `SUPER_ADMIN`으로 분리 | 개념이 직관적 | 로그인 이동·URL 규칙·기존 Role 비교를 광범위하게 수정 | 단독 적용 비권장 |
| Permission 기반 RBAC | 기능별 권한 묶음과 확장성이 좋음 | 초기 모델·테스트·운영 UI 설계가 필요 | 최종 구조로 권장 |

따라서 1차 구현은 `ADMIN + AdminLevel`로 최고관리자를 안전하게 식별하고, 동시에 아래 Permission 이름을 코드 정책으로 도입한다. 이후 관리자별 권한 커스터마이징이 필요할 때 DB 기반 Permission 할당으로 확장한다. `AdminLevel`만 곳곳에서 직접 비교하지 않고 Permission으로 변환해야 조건문 확산을 막을 수 있다.

## 3. 권한 설계 원칙

1. **기본 거부**: 명시적으로 허용되지 않은 기능과 데이터는 접근 불가다.
2. **기능 권한과 데이터 범위 분리**: “학생 조회 가능”과 “어느 학생까지 조회 가능”을 별도로 판정한다.
3. **서버가 최종 권한 판단**: UI 숨김은 편의 기능이며 보안 경계가 아니다.
4. **객체 단위 검사**: 목록뿐 아니라 상세·수정·삭제·파일·엑셀·상태 변경에서도 대상 과정/학생을 재검사한다.
5. **최소 권한**: 강사는 배정 범위, 운영관리자는 운영 범위, 최고관리자는 시스템 통제 범위만 가진다.
6. **민감정보 목적 제한**: 상담·생활·평가·취업 정보는 업무 목적, 조회 사유, 감사 로그를 적용한다.
7. **이력 보존**: 일지·상담·평가·수료·출결은 원본 덮어쓰기나 물리 삭제보다 정정 이력과 상태 변경을 사용한다.
8. **다운로드는 별도 권한**: 화면 조회가 가능해도 대량 다운로드는 자동 허용하지 않는다.
9. **통계 재식별 방지**: 익명 평가는 최소 응답 수와 자유서술 마스킹을 적용한다.
10. **프런트 신뢰 금지**: courseId, studentId, authorId를 요청에서 받더라도 로그인 사용자의 허용 범위를 서버에서 다시 계산한다.

### 3.1 네 단계 적용 원칙

| 계층 | 목적 | 필수 처리 |
|---|---|---|
| UI | 사용할 수 없는 메뉴·버튼으로 인한 혼란 방지 | Permission 기준 메뉴/버튼 숨김 또는 비활성 |
| URL | 주소 직접 입력 차단 | Route 수준 Role/Permission 검사, 불가 시 403 |
| Controller/API | 조작된 요청과 객체 ID 공격 차단 | 행위 Permission 및 대상 객체 범위 검사 |
| Query/Data | 목록·검색·다운로드에서 타 범위 데이터 유출 차단 | 허용 scope를 Query 조건에 강제, 전체 조회 후 메모리 필터링 금지 |

## 6. 데이터 Scope 매트릭스

### 6.1 권장 Scope 명칭

단순 `ALL`은 조직·서비스가 확장될 때 의미가 불명확하므로 `INSTITUTION_ALL`을 권장한다.

| Scope | 의미 | 산정 기준 |
|---|---|---|
| `INSTITUTION_ALL` | 현재 기관 전체 | 기관/테넌트 ID. 현재 단일 기관이면 전체 |
| `ASSIGNED_COURSE` | 로그인 사용자에게 배정된 과정 | 강사-과정 매핑 |
| `ASSIGNED_CLASS` | 배정된 반 | 반/분반 매핑. 현재 독립 반 모델이 없으면 구현 보류 |
| `ASSIGNED_STUDENT` | 담당 과정·반 또는 명시적 케이스 배정으로 연결된 학생 | 서버에서 파생, 요청값 신뢰 금지 |
| `ASSIGNED_CASE` | 본인에게 배정된 Q&A·튜터링·상담 케이스 | 담당자 매핑 |
| `OWN_RECORD` | 본인이 작성한 기록 | `createdBy`와 로그인 사용자 비교 |
| `SELF` | 본인 계정·본인 평가 결과 | 로그인 사용자 ID |
| `AGGREGATED_ANONYMOUS` | 개인을 식별할 수 없는 집계 결과 | 최소 표본·비식별 규칙 적용 |
| `NONE` | 접근 불가 | 항상 거부 |

`ASSIGNED_COURSE`, `ASSIGNED_CLASS`, `ASSIGNED_STUDENT`를 단순한 상하관계로만 구현하면 안 된다. 예를 들어 상담 케이스는 과정 배정과 별도로 담당자에게 배정될 수 있으므로 `ASSIGNED_CASE`가 필요하다.

## 7. 민감 기능 권한 정책

### 7.1 학생 일지

권장 데이터 분류는 두 축이다.

- 가시성: `AUTHOR_ONLY`, `CARE_TEAM`, `STUDENT_VISIBLE`
- 민감도: `STANDARD`, `SENSITIVE`, `HIGHLY_SENSITIVE`

권장 정책:

1. 강사는 담당 학생의 `CARE_TEAM` 기록만 조회하고, 다른 강사의 `AUTHOR_ONLY` 기록은 볼 수 없다.
2. 강사는 본인이 작성한 기록을 작성 후 24시간 또는 후속조치 생성 전까지만 수정한다.
3. 24시간 이후에는 원문을 덮어쓰지 않고 정정 사유와 새 버전을 남긴다.
4. 삭제는 기본 금지하고 `INVALIDATED` 상태와 사유를 남긴다. 법적·개인정보 삭제가 필요할 때만 최고관리자가 승인한다.
5. 운영관리자도 원문을 임의 수정하지 않고 정정 이력을 추가한다.
6. 건강, 심리, 가정, 징계 가능 정보는 `SENSITIVE` 이상으로 분류하고 열람 목적과 열람 로그를 남긴다.
7. 학생에게 공개할 내용은 작성 시 `STUDENT_VISIBLE`로 명시하며 내부 지도 메모와 분리한다.

### 7.2 상담·후속조치

권장 상태 흐름:

```text
관찰 필요 -> 상담 예정 -> 진행 중 -> 완료 요청 -> 완료
                         \-> 관리자 이관
완료 -> 재오픈(관리자 이상)
```

| 행위 | 강사 | 운영관리자 | 최고관리자 |
|---|---|---|---|
| 담당 학생 상담 생성 | O | O | O |
| 관찰/상담예정/진행중 변경 | O | O | O |
| 다른 강사에게 배정 | 요청만 | O | O |
| 완료 | 완료 요청 | 승인·완료 | O |
| 재오픈 | 요청 | O | O |
| 민감 생활상담 열람 | 담당+허용 기록 | 업무 목적 | 감사 대상 전체 |

긴급 위험 신호는 일반 상담과 분리하여 지정 관리자에게 즉시 알리고, 강사가 임의로 종결하지 못하게 한다.

### 7.3 강의평가·강사평가

1. 강사에게는 담당 과정 또는 본인 평가의 익명 집계만 제공한다.
2. 응답자 이름, 학번, 원문 접속 시각 등 재식별 단서는 제공하지 않는다.
3. 기본 최소 표본을 5명으로 제안한다. 미만이면 점수·주관식 모두 숨기거나 상위 기간과 합산한다.
4. 운영관리자는 교육 개선 업무에 필요한 과정·강사 집계를 조회한다.
5. 최고관리자는 기관 전체 비교와 추이를 조회하되 응답자 식별 권한은 갖지 않는 것을 원칙으로 한다.
6. 자유서술은 개인정보·비방 가능성을 자동/수동 검토한 뒤 강사에게 제공하고 원문은 제한 보관한다.
7. 평가 결과 다운로드는 화면 조회와 별도 Permission으로 분리한다.

### 7.4 공지·긴급 알림

| 발송 범위 | 강사 | 운영관리자 | 최고관리자 |
|---|---|---|---|
| 담당 과정/반 일반 공지 | O | O | O |
| 담당 과정/반 긴급 공지 | 조건부 | O | O |
| 여러 과정 공지 | X | O | O |
| 기관 전체 일반 공지 | X | O | O |
| 기관 전체 긴급 공지 | X | 승인 요청 또는 이중 승인 | O |

긴급 공지는 발송 취소가 어렵고 대량 알림 피해가 크므로 대상 인원 미리보기, 재확인, 발송자·승인자·내용·대상 로그를 남긴다.

### 7.5 취업·사후관리

강사가 볼 수 있는 항목은 교육 지도에 필요한 취업 목표, 포트폴리오 준비 상태, 상담 일정, 동의된 코칭 메모로 제한한다. 지원 기업별 민감 메모, 희망·확정 연봉, 채용 담당자 개인정보, 의료·가정·재정 정보, 정부 보고용 원본은 운영관리자 이상으로 제한한다.

수료 후 강사의 담당 관계가 끝나면 기본 열람 권한도 종료하고, 사후지도 담당자로 명시 배정된 경우에만 `ASSIGNED_STUDENT`를 유지한다.

### 7.6 리포트

| 리포트 단위 | 강사 | 운영관리자 | 최고관리자 |
|---|---|---|---|
| 개인 학생 | 담당 학생 | 전체 | 전체 |
| 반 | 담당 반 | 전체 | 전체 |
| 과정 | 담당 과정 | 전체 | 전체 |
| 강사 | 본인 집계 | 업무상 전체 | 전체 비교 |
| 기관 전체 | X | 운영 집계 | 전체·민감 비교 |

화면 조회, 인쇄, 엑셀/CSV 다운로드를 별도 권한으로 판정한다. 다운로드 파일에는 생성자·생성시각·필터·범위를 기록하고 민감 열은 기본 제외한다.

### 7.7 HRD·원본 데이터·관리자 권한

- HRD 원본, 업로드, 동기화, 오류 재처리는 운영관리자 이상만 허용한다.
- 강사에게 HRD 원본 관리 기능을 제공하지 않는다.
- 관리자 계정 생성·비활성, 관리자 등급 변경, Permission 부여·회수는 최고관리자만 수행한다.
- 최고관리자도 자신의 권한을 직접 승격하거나 마지막 최고관리자 계정을 비활성화할 수 없게 한다.
- 권한 변경과 민감 데이터 조회·다운로드는 변경 전후 값과 수행자를 감사 로그에 기록한다.

## 8. 향후 권한 구현 방식 제안

### 8.1 단계별 이행

**1단계: 즉시 보완**

1. 로그인 ID 기반 최고관리자 판별을 DB의 `AdminLevel` 또는 명시 권한으로 교체한다.
2. Method Security를 활성화하고 Permission 이름을 중앙 정의한다.
3. 현재 공백이 확인된 콘텐츠·문제은행·과제·시험 생성·설문 경로부터 객체 단위 검사를 추가한다.
4. 목록, 상세, 파일, 엑셀, 상태 변경에 같은 scope 정책을 적용한다.
5. 접근 거부 테스트를 정상 접근 테스트와 같은 비중으로 추가한다.

**2단계: 권한 서비스 통합**

```java
authorization.can(authentication, Permission.ASSIGNMENT_GRADE, resource)
authorization.require(authentication, Permission.STUDENT_DIARY_READ, studentId)
scopeResolver.allowedCourseIds(authentication)
```

Controller마다 `role == ADMIN` 조건을 복제하지 않고 중앙 `AuthorizationService`와 `ScopeResolver`를 사용한다. Service가 최종 객체 권한을 검사하고 Repository는 허용 ID 또는 기관 ID를 쿼리 조건으로 받는다.

**3단계: 운영 가능한 RBAC**

- 역할별 기본 Permission 묶음 도입
- 필요 시 관리자별 예외 Permission 부여
- 권한 변경 승인·감사 화면
- 민감 조회 사유 입력과 감사 로그
- 정책 회귀 테스트 자동화

### 8.2 권장 Permission 예시

```text
COURSE_READ, COURSE_MANAGE, COURSE_ASSIGN_INSTRUCTOR
STUDENT_READ, STUDENT_MANAGE, ENROLLMENT_APPROVE
CONTENT_READ, CONTENT_WRITE
ASSIGNMENT_MANAGE, ASSIGNMENT_GRADE, EXAM_MANAGE, EXAM_GRADE
ATTENDANCE_READ, ATTENDANCE_CORRECT_REQUEST, ATTENDANCE_CORRECT_APPROVE
STUDENT_DIARY_READ, STUDENT_DIARY_WRITE, STUDENT_DIARY_CORRECT
CARE_CASE_READ, CARE_CASE_WRITE, CARE_CASE_ASSIGN, CARE_CASE_CLOSE
NOTICE_WRITE, NOTICE_EMERGENCY_SEND
SURVEY_MANAGE, EVALUATION_AGGREGATE_READ
REPORT_READ, REPORT_EXPORT
HRD_MANAGE, ADMIN_ACCOUNT_MANAGE, PERMISSION_MANAGE
AUDIT_LOG_READ, SYSTEM_SETTING_MANAGE
```

### 8.3 테스트 기준

각 기능은 최소 다음 네 유형을 테스트한다.

1. 허용 Role + 허용 데이터 범위 = 성공
2. 허용 Role + 타 데이터 범위 = 403
3. 미허용 Role + 직접 URL/API 요청 = 403
4. 목록/검색/파일/다운로드에 타 범위 데이터가 포함되지 않음

특히 숫자 ID만 바꾼 상세·수정·삭제·파일 요청, 복수 ID 일괄 요청, 빈 scope, 배정 해제 직후, 관리자 등급 변경 직후를 포함한다.

## 9. 현재 구조에서 변경이 필요한 부분

이 절은 다음 구현 단계의 예상 범위이며 이번 문서 작업에서는 수정하지 않는다.

| 대상 | 예상 변경 |
|---|---|
| `user/entity/Role.java` | Role을 무조건 늘리기보다 현재 persona 유지 여부 확정 |
| 사용자/관리자 엔티티 및 DB migration | `AdminLevel` 또는 관리자 권한 관계 저장 |
| `auth/LoginUser.java` | Role 외 Permission/관리자 등급을 GrantedAuthority로 변환 |
| `config/SecurityConfig.java` | Method Security 활성화, Route Permission 정리 |
| `user/service/SuperAdminPolicy.java` | 로그인 ID 비교 제거, 명시 권한 검사로 교체 |
| 권한 공통 모듈(신규) | `Permission`, `DataScope`, `AuthorizationService`, `ScopeResolver` |
| 콘텐츠 Controller/Service | 담당 과정 객체 검사 추가 |
| 문제은행 Controller/Service/Entity | 소유자·공유 상태·승인·다운로드 권한 추가 |
| 과제 Controller/Service | 생성·상세·수정·마감·삭제·첨부파일의 scope 통일 |
| 시험 Controller/Service | 생성 시 담당 과정 검사 누락 보완 |
| 설문 Controller/Service | 목록·생성·수정·상태·삭제의 담당 과정 제한 |
| 관리자 계정 Controller/Service | 최고관리자 전용 서버 검사 적용 |
| 학생 케어 신규 모델 | 일지 가시성/민감도/버전, 상담 배정/상태/이력 |
| Repository | 기관·담당 과정·담당 학생 조건의 scoped query |
| 공통 관리자 템플릿 | Permission 기반 메뉴·버튼 노출. 서버 정책과 동일한 이름 사용 |
| 감사 로그 | 민감 조회·다운로드·권한 변경·정정 이력 확장 |
| 테스트 | Role×Permission×Scope 허용/거부 통합 테스트 |

구현 우선순위는 `현재 권한 공백 차단 → 최고관리자 식별 개선 → 공통 권한 서비스 → 민감 기능 도입 → 운영용 권한 관리` 순서를 권장한다.

## 10. [대표님 확인 필요]

아래 항목은 코드만으로 결정할 수 없는 운영 정책이다. 구현 전에 선택 결과를 문서에 반영해야 한다.

1. **학생 일지 공개 범위**: 학생이 볼 수 있는 일지를 별도 지정할지, 모든 일지를 내부 전용으로 할지.
2. **학생 일지 수정 시간**: 강사 자유 수정 가능 시간을 권장안 24시간으로 확정할지.
3. **학생 일지 상호 열람**: 담당 학생의 다른 강사 기록을 모두 볼지, `CARE_TEAM` 표시 기록만 볼지.
4. **민감 상담의 관리자 범위**: 모든 운영관리자가 볼지, 학생 케어 담당 관리자만 볼지.
5. **후속조치 완료 권한**: 강사가 일반 조치를 직접 완료할 수 있게 할지, 모든 완료에 관리자 승인을 요구할지.
6. **담당 강사 변경 후 과거 기록**: 기존 강사의 열람을 즉시 회수할지, 일정 기간 읽기만 허용할지.
7. **긴급 공지**: 강사의 담당 과정 긴급 발송을 허용할지, 관리자 승인을 요구할지.
8. **기관 전체 긴급 공지**: 운영관리자 단독 발송을 허용할지, 최고관리자 또는 2인 승인을 적용할지.
9. **강의·강사평가 최소 표본**: 권장 5명으로 확정할지, 다른 기준을 사용할지.
10. **강사평가 주관식 공개**: 원문 전체, 검수 후 공개, 요약만 공개 중 어느 방식인지.
11. **운영관리자의 강사평가 범위**: 모든 운영관리자가 전체 강사를 볼지, 담당 과정/조직으로 제한할지.
12. **취업정보 강사 공개 범위**: 지원 기업명·진행 단계·결과·연봉 중 어디까지 공개할지.
13. **수료 후 강사 접근 기간**: 담당 학생의 사후관리 정보를 언제까지 볼 수 있는지.
14. **운영관리자 계정 생성**: 최고관리자만 가능한지, 운영관리자가 생성 요청 후 최고관리자가 승인하는지.
15. **운영관리자별 권한 차등**: 모든 운영관리자가 같은 권한인지, 학생/교육/취업 등 담당 업무별 묶음이 필요한지.
16. **다운로드 승인 기준**: 학생 수, 민감 열 포함 여부 등에 따라 추가 승인을 요구할지.
17. **감독 녹화 보존·열람**: 보존 기간, 열람 사유, 열람 가능한 관리자 범위를 어떻게 정할지.
18. **물리 삭제 정책**: 일지·상담·평가·출결·수료 기록의 법정/내부 보존 기간과 파기 승인자를 누구로 할지.
19. **다중 최고관리자**: 최소 2명을 둘지, 마지막 최고관리자 보호와 비상 복구 절차를 어떻게 운영할지.
20. **반(분반) 개념**: 과정/기수와 별도의 반 엔티티 및 강사 배정이 필요한지.

---

이 설계의 핵심은 같은 관리자 화면을 사용하더라도 **행위 Permission과 데이터 Scope를 매 요청마다 함께 검사**하는 것이다. UI에서 메뉴를 숨기는 것만으로는 권한이 완성되지 않으며, URL·Controller/Service·Query·다운로드까지 동일한 정책을 적용해야 한다.
